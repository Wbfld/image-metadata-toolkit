# W02 TIFF/EXIF serialization decision record

W02 adds a reusable, bounded TIFF directory graph and an atomic classic
TIFF/BigTIFF writer. The graph is independent of image pixel decoding and is
available from the main package and `browser-image-metadata/tiff`.

## Public surface

```ts
import {
  parseTiffGraph,
  rewriteTiff,
  serializeTiff,
} from "browser-image-metadata/tiff";
```

`TiffGraph` contains byte order, the classic/BigTIFF variant, a root directory,
ordered directories, ordered entries, and relocatable payloads. Every parsed
entry retains its numeric tag, type, count, exact raw bytes, source span, and a
stable entry identity. Valid directory-pointer fields become explicit
directory references. Standard strip/tile and thumbnail offset/count pairs
become relocatable payload references; thumbnail bytes are retained without
decoding them.

`serializeTiff(graph)` validates the graph and writes a fresh byte array. It
never changes the graph or any supplied `Uint8Array`. Classic TIFF uses
two-byte directory counts, four-byte offsets, word alignment, and both II/MM
byte orders. BigTIFF uses the required 43 header, eight-byte counts/offsets,
20-byte entries, and eight-byte alignment.

`rewriteTiff(bytes, { edits })` parses a complete graph, applies typed entry
sets/deletes to an immutable working copy, recalculates every directory,
value, directory-pointer, and payload offset, serializes once, and reparses a
canonical serialization before returning. It supports changed TIFF type,
count, and encoded length. `duplicatePolicy` is explicit; the default
`replace-target` changes the first occurrence while preserving unrelated
entries. `canonical` ordering sorts by tag and stable entry identity.

The W01 `editMetadata()` API uses the same transaction engine for standalone
TIFF/BigTIFF input. Exact EXIF field IDs, including explicit directory/tag IDs
and existing normalized fields, support set/delete/copy/alias/rename. The
standalone TIFF/BigTIFF graph writer does not embed container metadata; JPEG,
PNG, and WebP embedding is provided by their dedicated W03–W05 writers. A
transaction with an unsupported, invalid, unsafe, or verification-failing
operation returns no output bytes; earlier planned operations are reported as
uncommitted rather than falsely reported as written.

## Safety and verification

All count, element-size, table-size, alignment, offset, output-size, directory,
entry, nesting, and preserved-payload arithmetic is checked before allocation.
Input and output limits use the package `SecurityLimits`; `maxOutputBytes`
defaults to `maxAdapterOutputBytes`. Unknown tags and unknown numeric type
codes are preserved as bounded raw entries. Unknown type codes are only
accepted with the conservative one-byte extent model and remain raw; malformed
directory pointers, truncated values, unsafe ranges, mismatched payload
offset/count arrays, and classic BigTIFF extensions are rejected before output.

Verification is a fixed-point check: the generated bytes must parse as a
complete bounded graph, and serializing that parsed graph must produce the
same bytes. `editMetadata()` additionally records input/output SHA-256 values,
rewritten ranges, directory relationships, and per-payload hashes. The caller's
input is copied before inspection and is never mutated.

The writer does not claim to preserve arbitrary unreferenced TIFF slack bytes.
It preserves all recognized directory values, unknown entry values, standard
image payloads, and EXIF thumbnails that are addressable by standard offset and
byte-count fields. Pixel data is copied as opaque bytes and is never decoded or
recompressed.
